Рабочий документ для владельца сервиса и для Клода в начале новой сессии
по проекту. Обновляется по ходу работы, в отличие от `DEPLOY.md`

## Общий статус проекта (на 2026-08-12)

**Что это.** Nasiya (бывш. «Финора») — CRM для учёта рассрочек (BNPL) для
торговых компаний: сделки, клиенты, платежи, касса, соинвесторы,
сотрудники, аналитика. Стек: Next.js 16 (App Router) + TypeScript +
Postgres. Деплой — собственный сервер на клиента (не общий SaaS с
поддоменами), управляется CLI `./nasiya install|update|settings|status|backup`
поверх Docker Compose (`app` + `db` + `caddy`).

**Где сейчас (в проде).** Один реальный сервер развёрнут и работает:
домен `nasiya.ru`, компания на `bakr.nasiya.ru`, IP `193.233.91.46` (см.
таблицу ниже). Переезд с localStorage-прототипа на Postgres завершён
(с 2026-08-08) — это уже история, а не открытая задача.

**Что реально работает (полный список фич — `PROGRESS.md`/`PROGRESS_PRO.md`,
здесь только веха):** канбан сделок, карточка сделки (график, экономика,
реструктуризация, откат платежа, досрочное закрытие, смена ответственного,
удаление ошибочной сделки, печать договора/сводки), карточка клиента с
оценкой надёжности, приём платежа, касса, соинвесторы (доля от прибыли,
журнал капитала), сотрудники, аналитика (воронка, лесенка просрочки,
причины отказов), клиентский кабинет `/pay/<token>`, маршрут менеджера
`/route`, рассылки-напоминания через WhatsApp, глобальный поиск.

**Что не работает / открыто прямо сейчас** — см. раздел «Статус по
открытым задачам» ниже; это текущий короткий список, а не всё, что
когда-либо было пробелом (полный исторический список — `PROGRESS.md`).

### Восстановление SSH-доступа (2026-08-12)

Пользователь прислал в чат `root`-пароль для входа по паролю. Доступ
восстановлен так: подобранный ранее ключ `~/.ssh/nasiya_admin` (созданный
до переустановки сервера) оказался всё ещё валидным на стороне клиента —
его публичную часть дописали в `~/.ssh/authorized_keys` на сервере через
разовый вход по паролю (через `sshpass`, поставлен через `brew install
sshpass`). Дальше — только по ключу, пароль больше не используется и
нигде не сохранён.

⚠️ **Пароль был передан открытым текстом в чате.** Рекомендация
пользователю: сменить root-пароль на сервере (`passwd`) и/или отключить
вход по паролю вовсе (`PasswordAuthentication no` в `sshd_config`) —
это как раз входит в задачу 5 (безопасность сервера), см. ниже.

## Фичи сверх исходных пяти задач

Начиная с 2026-08-12 — по итогам краткого анализа рынка (Payme Nasiya,
BILLZ и общие тренды BNPL-платформ) пользователь исключил кредитный лимит
и пеню за просрочку как решения, которых в системе никогда не будет, и
попросил список остальных вариантов. Взяли в работу первым — лесенку
напоминаний.

1. **Автоматическая лесенка напоминаний** — Статус: _готово, в проде_.
   - Раньше было ровно одно напоминание, которое менеджер собирал и
     отправлял вручную на каждой сделке. Теперь `/mailings` считает по
     графику каждой активной сделки, кому сегодня пора напомнить и каким
     тоном: `before` (за 1–3 дня), `due` (в день платежа), `overdue_soft`
     (просрочка 1–3 дня), `overdue_hard` (просрочка от 4 дней) —
     `lib/reminders.ts` → `computeReminderQueue()`. Отправка осталась
     ручной (клик по wa.me-ссылке) — своей интеграции с WhatsApp Business
     API у компании нет и не появится в этой архитектуре без отдельного
     контракта.
   - Миграция `db/migrations/tenant/011_reminder_ladder.sql`:
     `deals.last_reminder_stage`/`last_reminder_due_date` (не даёт
     напомнить дважды по тому же взносу), `message_templates.stage`
     (шаблон закреплён за стадией, один шаблон на стадию — при сохранении
     бэкенд сам снимает стадию с прежнего владельца), плюс 4 сид-шаблона
     под все стадии.
   - Проверено локально через прямую правку `opened_at`/`stage` тестовой
     сделки в БД: очередь корректно показала `due`, затем `overdue_hard`
     для той же сделки; после отправки карточка пропадала из очереди и
     `last_reminder_stage` записывался в БД.
   - **Задеплоено на прод 2026-08-12** (`./nasiya update`, коммит
     `81f1a98`).

2. **«Чёрный список»** — Статус: _готово, в проде_ (коммит `25644df`).
   Менеджер вручную отмечает клиента с карточки клиента (необязательная
   причина), список — отдельный пункт меню `/blacklist`. Ничего не
   блокирует: при выборе такого клиента в мастере создания сделки менеджер
   просто видит предупреждение с причиной и решает сам — осознанно не
   пересекается с отклонённым решением «кредитный лимит». Миграция
   `012_blacklist.sql` (`clients.blacklisted_at`/`blacklist_reason`).

3. **Редизайн входа** (2026-08-12) — `/login` и `/admin/login` (до его
   удаления) переведены на split-layout с иллюстрацией в фирменной
   палитре сайта, по образцу референса пользователя. Статус: _готово, в
   проде_ (коммиты `14923a5`, `3eb6b43`). Также добавлена кнопка «Выйти»
   в сайдбар CRM — раньше её не было вообще (коммит `4ec1ee1`).

4. **Панель владельца платформы (`/admin`) — удалена** (2026-08-12,
   коммит `8507045`). Она умела заводить несколько компаний на одной
   `nasiya_control` базе — при архитектуре «1 сервер = 1 компания» это
   было мёртвым функционалом (на сервере всегда ровно одна компания,
   заведённая через `./nasiya install`). Пользователь решил не
   поддерживать её и убрать совсем. Таблицы `platform_admins`/
   `platform_sessions` в control-базе остались (миграции только вперёд),
   но пустые и ни на что не влияют.
   **Взамен запланирована другая панель** — мониторинг ВСЕХ серверов
   клиентов (у каждого свой независимый VPS), не через общую БД, а через
   опрос `/api/health` каждого сервера отдельно. Статус: _в бэклоге,
   отложено пользователем 2026-08-12 ради «Чёрного списка»_. Решено при
   обсуждении:
   - Отдельное лёгкое приложение (не часть этого репозитория) на новом
     арендованном VPS, свой домен/поддомен.
   - Отдельный GitHub-репозиторий (например `nasiya-monitor`).
   - Механизм — панель сама периодически опрашивает `/api/health` каждого
     сервера из своего списка (не наоборот — сервера ничего никуда не
     шлют).
   - Не начато: список серверов и доступов панель должна хранить в своей
     БД (не в конфиг-файле), `/api/health` в `rassrochka` возможно стоит
     расширить (сейчас, вероятно, просто `{ok:true}` — версия
     деплоя/коммит и т.п. были бы полезны для панели).

5. **Единая ссылка кабинета клиента** — Статус: _готово, в проде_
   (коммит `fa736b3`). Раньше ссылка `/pay/<token>` была на каждую сделку
   отдельно — у клиента с 10 сделками было бы 10 ссылок, и новая сделка
   требовала новую ссылку. Теперь токен на клиенте
   (`clients.portal_token`, миграция `013_client_portal_token.sql`), одна
   ссылка показывает список всех активных/закрытых сделок (аккордеон —
   клик разворачивает полный график). Старые разосланные ссылки на
   конкретную сделку продолжают работать: `/api/portal/[token]` пробует
   сначала клиентский токен, потом токен сделки, тот же URL для обоих.
   Заодно убран график «Динамика остатка» на карточке сделки — пользователь
   счёл его лишним (дублировал таблицу графика платежей).

6. **Экспорт в CSV** — Статус: _готово, в проде_ (коммит `4e48482`).
   Первая фича из рыночного анализа (см. выше по разделу). Кнопка
   «Экспорт» на страницах «Клиенты» и «Кассы» выгружает текущий
   отфильтрованный список в CSV (`;`-разделитель и BOM — открывается
   Excel в русской локали без кракозябр). `lib/csv.ts` переиспользуем для
   следующих страниц, если понадобится. Остальные дешёвые фичи из
   рыночного анализа (NPS-опрос после закрытия сделки, SMS как резервный
   канал) — в бэклоге, не начаты.

7. **Гранулярные роли: «Бухгалтер»** — Статус: _готово, в проде_
   (коммит `5834e6b`). Средняя по сложности фича из рыночного анализа.
   Третья роль сотрудника (кроме admin/manager) — видит и может открыть
   только «Кассы» и «Аналитику», прямой переход по URL на другие разделы
   молча уводит на кассу (`components/shell.tsx`, `AccountantGate`).
   Ограничение не только визуальное: API создания/редактирования сделок
   и клиентов (сделки, приём платежа, реструктуризация, досрочное
   закрытие, смена ответственного, напоминания, чёрный список) проверяет
   роль на сервере (`app/api/_lib/handler.ts`, опция `roles`) — прямой
   запрос в обход интерфейса тоже получит 403. Движение по кассе
   (основная задача бухгалтера) не ограничено. Миграция
   `014_accountant_role.sql`. Проверено вручную: заведён тестовый
   бухгалтер, подтверждены редирект в интерфейсе, 403 на `/api/deals`,
   200 на `/api/cash` — тестовые данные удалены после проверки.

8. **Настройка видимости разделов меню + «Кассы» → «Финансы»** —
   Статус: _готово, в проде_ (коммит `45614d9`). `/settings` → «Разделы
   меню»: администратор скрывает любой пункт бокового меню (кроме самих
   «Настроек» — защита от случайной потери доступа), настройка общая на
   компанию (`settings.hidden_nav_items`), применяется у всех сразу.
   `PATCH /api/settings/nav` — adminOnly. Пункт «Кассы» переименован в
   «Финансы» (href `/cash` не менялся). `components/stub.tsx` удалён —
   последняя страница-заглушка (`/settings`) стала настоящей.
