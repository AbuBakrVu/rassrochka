# Финора — подробная техническая карта проекта

Этот файл — «спасательный круг» на случай заполнения контекстного окна
или новой сессии: прочитав только его, можно восстановить полное
понимание проекта без просмотра истории чата. `PROGRESS.md` рядом —
короткая версия для быстрого обзора; здесь — то же самое, но со всеми
деталями реализации, именами файлов и обоснованиями решений.

Обновляйте оба файла при значимых изменениях. Если решение поменялось —
правьте текст здесь, а не дописывайте противоречия в конец.

---

## 1. Что это за продукт

CRM «Финора» для небольшой компании, выдающей товары в рассрочку
(BNPL-подобная модель): менеджер заводит клиента, оформляет сделку на
товар с графиком равных ежемесячных платежей, отслеживает просрочки,
принимает оплаты, отправляет клиенту персональную ссылку на его график.

Референсы дизайна изначально — Podeli/«Долями»/Т-Банк Рассрочка (см.
переписку), но визуальный язык переработан под собственный светлый
финтех-стиль, не копия.

## 2. Стек и почему так

- **Next.js 16 (App Router, Turbopack)**, React 19, TypeScript, Tailwind 4.
- **Без бэкенда и без базы данных — осознанное решение.** Обсуждали
  переезд на VPS с managed Postgres; пользователь 2026-08-06 явно попросил
  остаться на локальном (браузерном) хранении, пока текущего объёма
  достаточно. На будущее пользователь предпочитает свой VPS, а не
  managed-облако — но пока не нужно поднимать ни то, ни другое.
- Иконки — **lucide-react**. Шрифт — **Inter** (`next/font/google`,
  подключены `latin` + `cyrillic`).
- Данные живут в браузере: `localStorage`, ключ `finora-store-v1`.
- Хостинг для разработки — локальный dev-сервер (`npm run dev`), запуска в
  проде/на сервере пока нет и не планируется в рамках текущего этапа.

## 5. Модель данных

### `Deal` (lib/data.ts)
```ts
interface Deal {
  id: string;            // "R-1042" — активные/новые из 2026, "R-0988" — исторически закрытые
  clientId: string;      // "C-101"
  client: string;        // денормализовано имя клиента (для быстрого рендера списков)
  product: string;
  amount: number;        // сумма, которая гасится графиком (ИТОГО минус первый взнос)
  months: number;
  openedAt: string;       // ISO-дата заключения; первый платёж = +1 месяц от неё
  stage: "new" | "check" | "signing" | "active" | "closed" | "rejected";
  status: string;          // человекочитаемый статус для бейджа ("В графике", "Отклонена"…)
  statusTone: "blue" | "yellow" | "green" | "red" | "gray";
  nextStep: string;         // текст следующего действия; у rejected — "Отказ: <причина>"
  deadline?: string;
  urgent?: boolean;
  manager: string;           // инициалы, напр. "АС"
}
```

**Важное упрощение:** наценка на страницах сделки/аналитики всегда
считается как **фиксированные 15% от `amount`** для отображения
(`markup = Math.round(deal.amount * 0.15)`), независимо от того, какая
наценка была реально введена в мастере создания сделки. Это унаследовано
с самого начала прототипа и осознанно не исправлялось — риск при
доработке: если когда-то захотите завязать реальную экономику, эту
формулу нужно менять одновременно в `components/deal-detail.tsx` и
`app/analytics/page.tsx`.

### `Client` (lib/data.ts)
```ts
interface Client {
  id: string;             // "C-101"
  name, phone, email, city, since: string;
  status: "active" | "overdue" | "closed" | "lead";
  statusLabel: string;
  nextAction: string;      // "—" если действий нет
  nextDate: string;
}
```
Клиенты, созданные через форму (`addClient`), получают `email: "—"`,
`city: "—"` — форма их не собирает (только ФИО, телефон, паспорт, адреса,
но `Client` эти поля не хранит).

### `dealState(deal)` vs `deal.stage`
`stage` — этап канбана (6 значений). `dealState()` — производное для
карточки клиента: `active`/`closed`/`rejected` как есть, а `new`/`check`/
`signing` схлопываются в `pending`.

### Расчёт графика — `buildSchedule(amount, months, paid, openedAt)`
Возвращает массив `Installment[]` — равные платежи, последний платёж
добирает остаток (защита от ошибок округления). `paid` — сколько платежей
уже отмечено оплаченными (см. ниже про `paidPayments`). Функция чистая,
не знает про стор — использует и CRM, и клиентский кабинет.

### `paidPayments: Record<dealId, number>`
Сколько платежей по сделке уже оплачено. Живёт в сторе, стартует с
`seedPaidPayments`. `paidCount(deal, paidPayments)` — у закрытых сделок
(`stage === "closed"`) всегда возвращает `deal.months` (считается
полностью выплаченной), иначе — значение из карты или `0`.

**Важно:** «Принять платёж» — что через модалку, что кнопкой на странице
сделки — всегда закрывает **ровно один** ближайший взнос целиком,
**игнорируя** сумму, которую пользователь ввёл вручную в поле. Это
согласовано с моделью равных платежей: частичные/произвольные платежи
не поддерживаются.

### ID-генерация (`lib/store.tsx: nextId`)
Ширина номера подстраивается под существующие id (не захардкожена):
клиенты — 3 цифры (`C-101` → следующий `C-116`), сделки — 4 цифры
(`R-0988`/`R-1055` → следующий `R-1056`). Баг с паддингом `C-0116` уже
находили и чинили — если увидите такое снова, значит кто-то вернул
`padStart(4, "0")` без учёта ширины существующих id.

## 6. Стор (`lib/store.tsx`) — как это работает

```
DataProvider (в app/layout.tsx, оборачивает <Shell>)
  useState<StoredShape>({ deals, clients, paidPayments })
  useEffect #1 (mount only): читает localStorage, если есть — заменяет state
  useEffect #2 (после hydrated=true): пишет state в localStorage при каждом изменении
  addDeal / addClient / acceptPayment — useCallback, мутируют через setState
  useData() — хук, бросает Error если вызван вне провайдера
```

**SSR-safe паттерн**: на сервере и при первом клиентском рендере всегда
используется затравка (`seedDeals`/`seedClients`/`seedPaidPayments`) —
чтобы не словить hydration mismatch. Только **после** монтирования читаем
`localStorage` и подменяем состояние (это вызывает второй, чисто
клиентский рендер — нормально и ожидаемо, не баг).

**Кто пишет в стор:** только три модалки —
`new-deal-modal.tsx` (addDeal + опционально addClient через
`new-client-modal`), `new-client-modal.tsx` (addClient, с опциональным
`onCreated` коллбэком — используется, когда форма открыта изнутри мастера
сделки, чтобы сразу выбрать созданного клиента), `accept-payment-modal.tsx`
и `deal-actions.tsx`/`deal-detail.tsx` (acceptPayment).

**Кто НЕ пишет в стор:** `restructure-modal.tsx` — визуальная имитация,
показывает успех и закрывается, но `months`/график сделки не меняет.
Причина: модель графика (`amount` + `months`) не рассчитана на
произвольный пересчёт задним числом с сохранением уже внесённых денег —
для честной реструктуризации нужна другая структура данных (список
фактических платежей вместо amount+months), это не сделано.

## 7. Динамические страницы: паттерн «тонкая серверная обёртка»

`/deals/[id]`, `/clients/[id]`, `/pay/[token]` устроены одинаково:

```tsx
// app/deals/[id]/page.tsx — весь файл
import DealDetail from "@/components/deal-detail";
export default async function DealPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return <DealDetail id={id} />;
}
```

Вся логика — в клиентском компоненте (`"use client"`), который берёт
данные через `useData()` и сам решает, что рендерить, если сущность не
найдена (свой `EmptyState`, не `next/navigation`'s `notFound()` — тот не
работает в клиентских компонентах). Раньше эти страницы были async
Server Components с `generateStaticParams()` и читали статический массив
напрямую — при переходе на стор это стало physически невозможным (сервер
не видит localStorage браузера), поэтому и понадобился этот рефакторинг.
Как следствие, при сборке (`next build`) эти три маршрута помечены `ƒ`
(динамические, server-rendered on demand), а не `○` (статические).

## 8. Хронология фич (для понимания, в каком порядке что появилось)

1. Прототип: Главная / Платежи / Сделки / Клиенты, светлый дизайн, мок-данные, приватный репозиторий GitHub.
2. Меню быстрых действий «+ Добавить» (CtaMenu в `ui.tsx`).
3. Форма нового клиента (визуальная, тогда ещё не сохраняла).
4. Мастер создания сделки, 4 шага (визуальный, тогда ещё не сохранял).
5. Страница сделки (паспорт/экономика/график/динамика остатка).
6. Окно «Принять платёж» (визуальное).
7. Клиентский кабинет `/pay/<token>`.
8. Карточка клиента с вкладками сделок по состоянию.
9. Оценка надёжности клиента (`assessRisk`) — прозрачный скоринг с объяснением.
10. Реструктуризация графика — визуальная (осталась такой).
11. Маршрут менеджера `/route`.
12. Реальная аналитика `/analytics`.
13. Глобальный поиск `⌘K`.
14. **Рефакторинг на реальное сохранение** — обнаружили, что формы ничего
    не сохраняют (два несвязанных источника моков для сервера и браузера),
    ввели `lib/store.tsx`, переписали 8 страниц/компонентов на чтение из
    стора, поймали и починили баг с паддингом id клиентов.
15. `PROGRESS.md`, затем этот файл.
16. Панель уведомлений (колокольчик в шапке) — раньше была заглушкой без
    обработчика клика. `buildNotifications()` в `lib/data.ts` переиспользует
    `buildRoute()` и переформатирует топ-6 приоритетных пунктов в ленту
    событий с моковыми relative-time метками (не настоящий event-лог —
    у сделок нет временных меток создания событий). Красная точка на
    колокольчике гаснет после первого открытия за сессию (локальный
    `useState`, не персистится — как и чек-лист `/route`).

## 9. Известные ограничения и пробелы

- **Нет бэкенда/БД** (см. §2) — данные не синхронизируются между
  устройствами и пользователями, живут в localStorage одного браузера.
- **Реструктуризация не персистится** (см. §6).
- **`Главная` и `Платежи` не подключены к стору** — используют отдельные
  decorative-моки (`kpi`, `priorities`, `newRequests`, `deadlines`,
  `inflowChart`, `todayAgenda`, `calendarDays` в `lib/data.ts`), которые
  не реагируют на создание сделок/клиентов. Это осознанно не трогали при
  рефакторинге — не было явного запроса, а объём был и так большой.
- **Пустые заглушки без функциональности**: Рассылки, Соинвесторы, Кассы,
  Реестр клиентов, Сотрудники, Настройки (`components/stub.tsx`).
- **Нет онлайн-оплаты** в клиентском кабинете — только «Позвонить»/
  «Написать».
- **Нет авторизации** — единственный подразумеваемый пользователь
  «Алексей» (имя захардкожено на Главной).
- **Чек-лист «Выполнено» на `/route`** — локальный `useState` в
  компоненте, не сохраняется в стор, сбрасывается при перезагрузке
  страницы (это по мокапу ожидаемо — маршрут «на сегодня»).
- Из 10 предложенных пользователем идей для развития (см. историю чата)
  реализовано 5: оценка надёжности, реструктуризация (частично —
  визуально), маршрут менеджера, реальная аналитика, `⌘K`. Не сделаны:
  лестница просрочки (aging buckets), кредитный лимит на клиента,
  автоматическая эскалация напоминаний по дням, расчёт пени за
  просрочку, онлайн-оплата в кабинете клиента.

## 10. Рабочие конвенции

- **После каждой проверенной фичи**: `npx next build` (или хотя бы
  `npx tsc --noEmit`) → проверка в браузере → `git commit` → `git push`.
  Не копить несколько фич в один пуш — так договорились с пользователем.
- Коммиты на русском, с `Co-Authored-By: Claude <модель> <noreply@anthropic.com>`.
- Дев-сервер запускается через `.claude/launch.json`, конфигурация
  `finora-dev` (`npm run dev`, `autoPort: true` — порт 3000 иногда занят
  другим процессом, тогда сервер поднимается на случайном свободном).
- Репозиторий: `github.com/AbuBakrVu/rassrochka`, приватный.
- При тестировании в браузере через инструменты автоматизации иногда
  наблюдалась многосекундная задержка обработки кликов из-за нагрузки на
  систему (не баг приложения) — если клики «не срабатывают», сначала
  проверить `requestAnimationFrame` задержку и нагрузку процессов, а не
  сразу чинить код.

## 11. Если контекст сжался и вы (модель) читаете это заново

1. Прочитайте `PROGRESS.md` (короче) или этот файл (подробнее) — не
   спрашивайте пользователя «расскажите, что уже сделано».
2. Проверьте `git log --oneline` и `git status` — они всегда отражают
   актуальное состояние, этот файл мог чуть отстать.
3. Прежде чем предлагать бэкенд/БД/сервер — вспомните §2: это уже
   обсуждали и осознанно отложили.
4. Если пользователь просит «почему сделка не создаётся» или похожее —
   сначала проверьте, что фича действительно подключена к
   `lib/store.tsx`, а не тянет старые статические `deals`/`clients` из
   `lib/data.ts` напрямую (последних больше не существует под этими
   именами — теперь `seedDeals`/`seedClients`, специально переименованы,
   чтобы такая ошибка была заметна на этапе тайпчека).
