## 1. Что это за продукт

CRM «Финора» для небольшой компании, выдающей товары в рассрочку
(BNPL-подобная модель): менеджер заводит клиента, оформляет сделку на
товар с графиком равных ежемесячных платежей, отслеживает просрочки,
принимает оплаты, отправляет клиенту персональную ссылку на его график.

Референсы дизайна изначально — Podeli/«Долями»/Т-Банк Рассрочка (см.
переписку), но визуальный язык переработан под собственный светлый
финтех-стиль, не копия.

- Иконки — **lucide-react**. Шрифт — **Inter** (`next/font/google`,

  проде/на сервере пока нет и не планируется в рамках текущего этапа.

## 5. Модель данных

### `Deal` (lib/data.ts)
```ts
interface Deal {
  id: string;            // "R-1042" — активные/новые из 2026, "R-0988" — исторически закрытые
  clientId: string;      // "C-101"
  client: string;        // денормализовано имя клиента (для быстрого рендера списков)
  product: string;
  amount: number;        // сумма, которая гасится графиком (ИТОГО минус первый взнос)
  months: number;
  openedAt: string;       // ISO-дата заключения; первый платёж = +1 месяц от неё
  stage: "new" | "check" | "signing" | "active" | "closed" | "rejected";
  status: string;          // человекочитаемый статус для бейджа ("В графике", "Отклонена"…)
  statusTone: "blue" | "yellow" | "green" | "red" | "gray";
  nextStep: string;         // текст следующего действия; у rejected — "Отказ: <причина>"
  deadline?: string;
  urgent?: boolean;
  manager: string;           // инициалы менеджера, совпадают с Employee.id, напр. "АС"
  markupPct: number;         // реальная наценка сделки в %, введена при создании
}
```

**Наценка — реальное поле, не константа.** Раньше наценка на страницах
сделки/аналитики везде считалась как фиксированные 15% от `amount`, хотя
мастер сделки уже спрашивал процент в поле «Наценка» и просто не сохранял
его (типичный «мёртвый» ввод). Теперь `markupPct` идёт в `addDeal` (см. §6)
и используется одной и той же формулой везде: `markup = Math.round(amount *
markupPct / 100)`, `purchase = amount - markup`. Три места, которые обязаны
использовать именно `deal.markupPct`, а не свою константу — `lib/cash.ts`
(`purchasePrice`), `components/deal-detail.tsx` («Экономика сделки») и
`app/analytics/page.tsx` (прибыль). Все затравочные сделки получили
`markupPct: 15` (та же цифра, что раньше была захардкожена).

### `Client` (lib/data.ts)
```ts
interface Client {
  id: string;             // "C-101"
  name, phone, email, city, since: string;
  status: "active" | "overdue" | "closed" | "lead";
  statusLabel: string;
  nextAction: string;      // "—" если действий нет
  nextDate: string;
}
```
Клиенты, созданные через форму (`addClient`), получают `email: "—"`,
`city: "—"` — форма их не собирает (только ФИО, телефон, паспорт, адреса,
но `Client` эти поля не хранит).

### `CashTx` (lib/store.tsx) — касса
```ts
interface CashTx {
  id: string;
  kind: "purchase" | "payment" | "adjustment";
  amount: number;   // отрицательная — расход, положительная — приход
  date: string;     // ISO
  dealId?: string;  // есть у purchase/payment, нет у ручных adjustment
  title: string;
  note?: string;
}
```
Остаток кассы = `CASH_OPENING_BALANCE` (1 240 000 ₽, захардкожено в
`lib/store.tsx`) + сумма всех `amount`. Закупочная цена сделки считается
той же формулой, что и «Экономика сделки» — `purchasePrice(deal)` в
`lib/cash.ts` вычитает `deal.markupPct` в обратную сторону
(`amount - amount*markupPct/100`), так что цифры на странице сделки и в
кассе всегда совпадают. `buildSeedCash()` восстанавливает правдоподобную
историю операций по затравочным сделкам при первом запуске (иначе касса
на чистом сторе выглядела бы пустой, хотя портфель уже не с нуля).

### `DealEvent` (lib/store.tsx / lib/events.ts) — история сделки
```ts
interface DealEvent {
  id: string;
  dealId: string;
  date: string;   // ISO
  text: string;
}
```
Карточка «История» на `/deals/[id]` раньше собирала 1-2 строки на лету из
`paid`/`stage` — не настоящий лог, а угадывание задним числом. Теперь
`events` — часть стора, пополняется реальными действиями (`addDeal` пишет
событие создания, `acceptPayment` — событие о каждом принятом платеже),
`dealEvents(events, dealId)` в `lib/events.ts` отдаёт их отсортированными
новые-сверху. `buildSeedEvents()` восстанавливает правдоподобную историю
для затравочных сделок (та же идея, что `buildSeedCash()` для кассы) —
иначе у всех сид-сделок «История» была бы пустой при первом запуске.

### `Employee` (lib/data.ts) — сотрудники
```ts
interface Employee {
  id: string;      // "АС" — те же инициалы, что уже жили в Deal.manager
  name, role, phone, email, since: string;
}
```
`seedEmployees` — статический список из 3 менеджеров, `id` выбраны так,
чтобы совпадать с уже существовавшими значениями `Deal.manager` в
затравочных сделках — не понадобилась миграция/маппинг id при добавлении
модели. `computeEmployees(deals, paidPayments)` (`lib/derive.ts`) считает
по каждому сотруднику: активные/просрочки/новые/закрытые/отказы, портфель
и собранное (через `computeActive`), топ-3 приоритетных дела (через
`buildRoute`, отфильтрованные по `deal.manager === employee.id`). Список
сотрудников не редактируется через UI — только выбор ответственного при
создании сделки (`new-deal-modal.tsx`, шаг «Условия»).

### Лестница просрочки — `computeAging` (lib/derive.ts)
Бьёт активные просроченные сделки на корзины 1–7/8–30/30+ дней. Просрочку
определяет **не** сравнение дат графика с `TODAY_ISO`, а тот же признак,
что и везде в приложении (Главная/Маршрут/Сотрудники/таблица нагрузки на
`/analytics`) — `deal.statusTone === "red"` на активном этапе. Причина:
дата ближайшего неоплаченного взноса в моках иногда совпадает с
`TODAY_ISO` (взнос ещё формально не просрочен по календарю), хотя сделка
уже помечена красной — если считать чисто по датам, «Лестница просрочки»
показала бы 0 сделок, а таблица «Нагрузка по сотрудникам» рядом — 1,
что выглядело бы как баг. Число дней просрочки при этом всё равно берётся
из графика (`today - next.iso`), с полом в 1 день на случай, когда дата
графика ещё не в прошлом. При добавлении новых просроченных сделок через
обычный жизненный цикл стора (а не мок) учтите: `addDeal`/`acceptPayment`
не выставляют `statusTone` автоматически — сейчас это исключительно
свойство мок-данных.

### `dealState(deal)` vs `deal.stage`
`stage` — этап канбана (6 значений). `dealState()` — производное для
карточки клиента: `active`/`closed`/`rejected` как есть, а `new`/`check`/
`signing` схлопываются в `pending`.

### Расчёт графика — `buildSchedule(amount, months, paid, openedAt)`
Возвращает массив `Installment[]` — равные платежи, последний платёж
добирает остаток (защита от ошибок округления). `paid` — сколько платежей
уже отмечено оплаченными (см. ниже про `paidPayments`). Функция чистая,
не знает про стор — использует и CRM, и клиентский кабинет.

### `paidPayments: Record<dealId, number>`
Сколько платежей по сделке уже оплачено. Живёт в сторе, стартует с
`seedPaidPayments`. `paidCount(deal, paidPayments)` — у закрытых сделок
(`stage === "closed"`) всегда возвращает `deal.months` (считается
полностью выплаченной), иначе — значение из карты или `0`.

**Важно:** «Принять платёж» — что через модалку, что кнопкой на странице
сделки — всегда закрывает **ровно один** ближайший взнос целиком,
**игнорируя** сумму, которую пользователь ввёл вручную в поле. Это
согласовано с моделью равных платежей: частичные/произвольные платежи
не поддерживаются.

### ID-генерация (`lib/store.tsx: nextId`)
Ширина номера подстраивается под существующие id (не захардкожена):
клиенты — 3 цифры (`C-101` → следующий `C-116`), сделки — 4 цифры
(`R-0988`/`R-1055` → следующий `R-1056`). Баг с паддингом `C-0116` уже
находили и чинили — если увидите такое снова, значит кто-то вернул
`padStart(4, "0")` без учёта ширины существующих id.

## 6. Стор (`lib/store.tsx`) — как это работает

```
DataProvider (в app/layout.tsx, оборачивает <Shell>)
  useState<StoredShape>({ deals, clients, paidPayments, cash, events })
  useEffect #1 (mount only): читает localStorage, мержит с затравкой
                              (см. ниже про смену схемы), заменяет state
  useEffect #2 (после hydrated=true): пишет state в localStorage при каждом изменении
  addDeal / addClient / acceptPayment / addCashAdjustment — useCallback, мутируют через setState
  useData() — хук, бросает Error если вызван вне провайдера
```

**SSR-safe паттерн**: на сервере и при первом клиентском рендере всегда
используется затравка (`seedDeals`/`seedClients`/`seedPaidPayments`,
касса — `buildSeedCash()`, история — `buildSeedEvents()`) — чтобы не
словить hydration mismatch. Только **после** монтирования читаем
`localStorage` и подменяем состояние (это вызывает второй, чисто
клиентский рендер — нормально и ожидаемо, не баг).

**Смена схемы стора.** Ключ `localStorage` версионирован
(`finora-store-v3`) — когда в `StoredShape` добавляется новое поле (как
`cash`, затем `events`), ключ бампается, а чтение сохранённых данных
**мержится** с затравкой по каждому полю отдельно (`saved.events ??
buildSeedEvents(...)`), а не подставляется целиком. Так старые сохранения
в браузере пользователя не роняют приложение с `TypeError: ... is not
iterable` — это реальный баг, который встретился при разработке (hot-reload
успел записать промежуточную схему в localStorage). При следующем
добавлении поля в `StoredShape` — либо повторить этот паттерн мержа, либо
снова бампнуть версию ключа.

**Кто пишет в стор:** четыре модалки —
`new-deal-modal.tsx` (addDeal + опционально addClient через
`new-client-modal`; addDeal попутно списывает закупочную цену из кассы и
пишет событие «Сделка создана» в `events`), `new-client-modal.tsx`
(addClient, с опциональным `onCreated` коллбэком — используется, когда
форма открыта изнутри мастера сделки, чтобы сразу выбрать созданного
клиента), `accept-payment-modal.tsx` и `deal-actions.tsx`/`deal-detail.tsx`
(acceptPayment, попутно приходует платёж в кассу и пишет событие о платеже
в `events`), `app/cash/page.tsx` (addCashAdjustment — ручное
внесение/изъятие).

**Кто НЕ пишет в стор:** `restructure-modal.tsx` — визуальная имитация,
показывает успех и закрывается, но `months`/график сделки не меняет.
Причина: модель графика (`amount` + `months`) не рассчитана на
произвольный пересчёт задним числом с сохранением уже внесённых денег —
для честной реструктуризации нужна другая структура данных (список
фактических платежей вместо amount+months), это не сделано.

## 7. Динамические страницы: паттерн «тонкая серверная обёртка»

`/deals/[id]`, `/clients/[id]`, `/pay/[token]` устроены одинаково:

```tsx
// app/deals/[id]/page.tsx — весь файл
import DealDetail from "@/components/deal-detail";
export default async function DealPage({ params }: { params: Promise<{ id: string }> }) {
  const { id } = await params;
  return <DealDetail id={id} />;
}
```

Вся логика — в клиентском компоненте (`"use client"`), который берёт
данные через `useData()` и сам решает, что рендерить, если сущность не
найдена (свой `EmptyState`, не `next/navigation`'s `notFound()` — тот не
работает в клиентских компонентах). Раньше эти страницы были async
Server Components с `generateStaticParams()` и читали статический массив
напрямую — при переходе на стор это стало physически невозможным (сервер
не видит localStorage браузера), поэтому и понадобился этот рефакторинг.
Как следствие, при сборке (`next build`) эти три маршрута помечены `ƒ`
(динамические, server-rendered on demand), а не `○` (статические).

**Ловушка с префиксами путей.** `components/shell.tsx` скрывает CRM-обо́лочку
на клиентском кабинете проверкой пути. Проверка обязана быть
`pathname.startsWith("/pay/")` — **со слэшем**. Без него под условие
попадал и раздел `/payments` (`"/payments".startsWith("/pay") === true`),
из-за чего на странице платежей пропадало всё меню и из неё нельзя было
никуда уйти. Ту же осторожность держать при добавлении новых разделов:
подсветка активного пункта меню тоже работает через `startsWith(href)`,
так что новый путь не должен быть префиксом существующего (или наоборот).

### Печать документов — `components/deal-print.tsx`

Кнопки «Договор рассрочки» / «Сводка по сделке» в карточке сделки (раньше
декоративные, с иконкой скачивания и без обработчика) вызывают
`window.print()` с версией только для печати:

```
deal-detail.tsx: print(mode) {
  flushSync(() => setPrintMode(mode));  // гарантирует, что DOM уже обновлён
  window.print();                        // до вызова window.print()
}
```

`flushSync` из `react-dom` обязателен: обычный `setState` + сразу
`window.print()` в React 18 может напечатать старый DOM, потому что
рендер батчится и не гарантированно завершается до синхронного вызова
`print()`. `DealPrint` рендерится через `createPortal(..., document.body)`
и виден только в `@media print` (`hidden print:block` в Tailwind) — на
экране не мешает разметке. Весь обычный интерфейс на печати скрывается
целиком через `print:hidden` на корневом `<div>` в `components/shell.tsx`,
так что печатается только контент портала. После печати состояние
сбрасывается по событию `window.addEventListener("afterprint", ...)`.

При добавлении печати на других страницах — повторить тот же паттерн
(`flushSync` + портал + `print:hidden` на обёртке), а не пытаться печатать
текущую страницу «как есть»: в интерфейсе слишком много декоративных
элементов (сайдбар, кнопки, тени), которые не нужны на бумаге.

## 8. Хронология фич (для понимания, в каком порядке что появилось)

1. Прототип: Главная / Платежи / Сделки / Клиенты, светлый дизайн, мок-данные, приватный репозиторий GitHub.
2. Меню быстрых действий «+ Добавить» (CtaMenu в `ui.tsx`).
3. Форма нового клиента (визуальная, тогда ещё не сохраняла).
4. Мастер создания сделки, 4 шага (визуальный, тогда ещё не сохранял).
5. Страница сделки (паспорт/экономика/график/динамика остатка).
6. Окно «Принять платёж» (визуальное).
7. Клиентский кабинет `/pay/<token>`.
8. Карточка клиента с вкладками сделок по состоянию.
9. Оценка надёжности клиента (`assessRisk`) — прозрачный скоринг с объяснением.
10. Реструктуризация графика — визуальная (осталась такой).
11. Маршрут менеджера `/route`.
12. Реальная аналитика `/analytics`.
13. Глобальный поиск `⌘K`.
14. **Рефакторинг на реальное сохранение** — обнаружили, что формы ничего
    не сохраняют (два несвязанных источника моков для сервера и браузера),
    ввели `lib/store.tsx`, переписали 8 страниц/компонентов на чтение из
    стора, поймали и починили баг с паддингом id клиентов.
15. `PROGRESS.md`, затем этот файл.
16. Панель уведомлений (колокольчик в шапке) — раньше была заглушкой без
    обработчика клика. `buildNotifications()` в `lib/data.ts` переиспользует
    `buildRoute()` и переформатирует топ-6 приоритетных пунктов в ленту
    событий с моковыми relative-time метками (не настоящий event-лог —
    у сделок нет временных меток создания событий). Красная точка на
    колокольчике гаснет после первого открытия за сессию (локальный
    `useState`, не персистится — как и чек-лист `/route`).
17. Главная и Платежи переведены с декоративных моков на расчёт из стора
    (`lib/derive.ts`) — последние два экрана, не реагировавшие на созданные
    сделки. Осиротевшие моки (`kpi`, `priorities`, `todayAgenda`,
    `calendarDays` и др.) удалены из `lib/data.ts`.
18. Кассы (`/cash`) — реальная лента операций (`lib/cash.ts`): закупка при
    создании сделки, приход при платеже, ручные корректировки. Баланс в
    мастере сделки перестал быть захардкоженным.
19. Сотрудники (`/employees`) — карточки менеджеров с реальной статистикой
    (`computeEmployees`, `lib/derive.ts`); мастер создания сделки получил
    обязательный выбор «Ответственный» (`Employee`/`seedEmployees` в
    `lib/data.ts`), значение пишется в `Deal.manager` вместо захардкоженного
    `"АС"`.
20. Лестница просрочки на `/analytics` (`computeAging`, `lib/derive.ts`) —
    корзины 1–7/8–30/30+ дней с суммой и списком сделок. Признак
    просроченности — тот же `statusTone === "red"`, что использует весь
    остальной код (важно: чисто дневной расчёт по датам графика иногда
    расходится с этим флагом на мок-данных, см. §5 `Employee`/aging).
21. **Смена рабочего процесса**: пользователь 2026-08-08 попросил не
    коммитить после каждой фичи, а копить несколько проверенных фич в один
    коммит/пуш — экономия токенов. С этого момента коммит делается пачкой,
    но сборка/тайпчек/браузерная проверка — по-прежнему после каждой фичи
    по отдельности, до коммита.
22. История сделки (`lib/events.ts`, поле `events` в сторе) — карточка
    «История» на `/deals/[id]` перестала быть выдумкой на лету и показывает
    реальный лог: создание сделки, каждый принятый платёж. `addDeal` и
    `acceptPayment` пишут события так же, как пишут в кассу.
23. Печать документов (`components/deal-print.tsx`) — кнопки «Договор
    рассрочки»/«Сводка по сделке» в карточке сделки (раньше декоративные)
    вызывают `window.print()` с версией только для печати; см. подробности
    в §7.
24. Настраиваемая наценка (`Deal.markupPct`) — мастер сделки уже спрашивал
    процент наценки в поле «Наценка», но никуда его не сохранял: везде в
    приложении наценка всё равно считалась как фиксированные 15%. Теперь
    `markupPct` — реальное поле сделки, используется одной формулой в
    `deal-detail.tsx`, `lib/cash.ts` и `app/analytics/page.tsx`.

## 9. Известные ограничения и пробелы

- **Нет бэкенда/БД** (см. §2) — данные не синхронизируются между
  устройствами и пользователями, живут в localStorage одного браузера.
- **Реструктуризация не персистится** (см. §6).
- **Пустые заглушки без функциональности**: Рассылки, Соинвесторы,
  Реестр клиентов, Настройки (`components/stub.tsx`). Кассы и Сотрудники
  теперь работают (см. §8, п.18-19).
- **Нет онлайн-оплаты** в клиентском кабинете — только «Позвонить»/
  «Написать».
- **Нет авторизации** — единственный подразумеваемый пользователь
  «Алексей» (имя захардкожено на Главной).
- **Чек-лист «Выполнено» на `/route`** — локальный `useState` в
  компоненте, не сохраняется в стор, сбрасывается при перезагрузке
  страницы (это по мокапу ожидаемо — маршрут «на сегодня»).
- Из первого набора 10 предложенных идей реализовано 8 (см. §8, п.1-20):
  оценка надёжности, реструктуризация (частично — визуально), маршрут
  менеджера, реальная аналитика, `⌘K`, кассы, сотрудники, лестница
  просрочки. Не сделаны: кредитный лимит на клиента, автоматическая
  эскалация напоминаний по дням, расчёт пени за просрочку, онлайн-оплата в
  кабинете клиента — от этих 4 отказались, пользователь запросил новый
  список.
- Из второго набора 10 идей (резервное копирование, экспорт CSV/Excel,
  заметки к сделке/клиенту, история сделки, печать/PDF, массовые действия
  на канбане, drag-and-drop, настраиваемая наценка, сохранённые фильтры,
  тёмная тема) реализовано 3: история сделки, печать/PDF, настраиваемая
  наценка (см. §8, п.22-24). Остальные 7 не начаты.

## 10. Рабочие конвенции

- **Проверка после каждой фичи**: `npx next build` (или хотя бы
  `npx tsc --noEmit`) → проверка в браузере.
- **Коммит и `git push` — пачкой**, после нескольких проверенных фич
  (с 2026-08-08 по просьбе пользователя, см. §8 п.21) — один коммит на всю
  пачку, а не один коммит на фичу. До этой даты действовало обратное
  правило («после каждой фичи») — если видите в git-истории смесь обоих
  стилей, это ожидаемо.
- Коммиты на русском, с `Co-Authored-By: Claude <модель> <noreply@anthropic.com>`.
- Дев-сервер запускается через `.claude/launch.json`, конфигурация
  `finora-dev` (`npm run dev`, `autoPort: true` — порт 3000 иногда занят
  другим процессом, тогда сервер поднимается на случайном свободном).
- Репозиторий: `github.com/AbuBakrVu/rassrochka`, приватный.
- При тестировании в браузере через инструменты автоматизации иногда
  наблюдалась многосекундная задержка обработки кликов из-за нагрузки на
  систему (не баг приложения) — если клики «не срабатывают», сначала
  проверить `requestAnimationFrame` задержку и нагрузку процессов, а не
  сразу чинить код.

## 11. Если контекст сжался и вы (модель) читаете это заново

1. Прочитайте `PROGRESS.md` (короче) или этот файл (подробнее) — не
   спрашивайте пользователя «расскажите, что уже сделано».
2. Проверьте `git log --oneline` и `git status` — они всегда отражают
   актуальное состояние, этот файл мог чуть отстать.
3. Бэкенд/БД/сервер — уже согласованное направление, см. `MIGRATION.md`
   (решение от 2026-08-08). Не отговаривайте от него, ссылаясь на старое
   «localStorage достаточно» — оно отменено.
4. Если пользователь просит «почему сделка не создаётся» или похожее —
   сначала проверьте, что фича действительно подключена к
   `lib/store.tsx`, а не тянет старые статические `deals`/`clients` из
   `lib/data.ts` напрямую (последних больше не существует под этими
   именами — теперь `seedDeals`/`seedClients`, специально переименованы,
   чтобы такая ошибка была заметна на этапе тайпчека).
