# Перенос «Финоры» на виртуальный сервер

План перевода прототипа (Next.js + localStorage, без бэкенда) в
многопользовательский SaaS на своём VPS: Postgres, авторизация, изоляция
компаний по поддоменам, Docker.

Читать вместе с `PROGRESS_PRO.md` — там текущее состояние кода, здесь целевое.

---

## 0. Вводные и принятые решения

**Масштаб первого года:** до 10 компаний, до 5 сотрудников внутри каждой —
около 50 пользователей суммарно. Это очень мало, и почти все архитектурные
решения ниже вытекают именно отсюда.

| Решение | Выбор | Почему |
|---|---|---|
| Топология | Один VPS на всех клиентов | 50 пользователей не грузят даже слабый сервер; N серверов = N деплоев ради простаивающего железа |
| Изоляция | Отдельная БД Postgres на компанию | Утечка из-за забытого `WHERE` становится невозможной; `pg_dump` на клиента работает из коробки |
| Разделение клиентов | Поддомен `company.finora.ru` | Домен определяет БД до всякой бизнес-логики |
| Контейнеризация | Docker Compose | Воспроизводимый деплой и откат. **Не** средство изоляции клиентов |
| Веб-сервер | Caddy | Автоматический TLS, простой конфиг, умеет выдавать сертификаты под поддомены по требованию |
| Авторизация | Своя, на сессиях в БД | ~150 строк против борьбы адаптеров Auth.js с БД-на-тенанта |

**Отложено осознанно:** Kubernetes, отдельный сервер БД, реплики, CI/CD с
автодеплоем, горизонтальное масштабирование. На 50 пользователях это чистые
накладные расходы. Вернуться, когда компаний станет больше 30–40.

**Порог перехода на другую модель:** если компаний станет ~50+, отдельные БД
начнут мешать (миграции по кругу, лимит соединений). Тогда — переезд на общую
БД с `company_id` и Postgres RLS. Это осознанная будущая миграция, а не то,
что нужно закладывать сейчас.

## 1. Что нужно решить до начала работ

### 1.1 Где хостить — проверить требования по персональным данным

Форма нового клиента собирает **паспортные данные**. Это персональные данные
в смысле 152-ФЗ, причём чувствительные. Законодательство требует, чтобы базы
с персональными данными граждан РФ находились на территории РФ.

**Это не юридическая консультация** — но прежде чем выбирать хостинг,
проверьте требование с юристом. Практический вывод: скорее всего нужен
российский провайдер (Selectel, Timeweb, Beget, VK Cloud, Yandex Cloud), а не
Hetzner/Contabo. Заодно и задержки до клиентов будут меньше.

Если окажется, что паспортные данные хранить не обязательно — проще вообще
перестать их собирать, тогда требования мягче.

### 1.2 Характеристики сервера

Для 50 пользователей с запасом:

- 2 vCPU, 4 ГБ RAM, 60 ГБ SSD
- Ubuntu LTS
- Резервные копии самого VPS средствами провайдера (не заменяют `pg_dump`, см. §8)

Больше не нужно: Next.js в standalone-сборке ест ~150 МБ, Postgres с такими
объёмами — ещё меньше. Основной расход RAM пойдёт на сборку, её лучше делать
не на сервере (см. §7.3).

### 1.3 Домен и DNS

- `finora.ru` — A-запись на IP сервера
- `*.finora.ru` — A-запись (wildcard) на тот же IP

Wildcard в DNS нужен всегда. А вот wildcard-**сертификат** — не обязательно,
см. §7.2, там способ обойтись без API-токена DNS-провайдера.

## 2. Целевая архитектура

```
                    Интернет
                       │
                 ┌─────▼─────┐
                 │   Caddy   │  TLS, маршрутизация по Host
                 └─────┬─────┘
                       │
                 ┌─────▼─────┐
                 │  Next.js  │  middleware: Host → slug компании
                 │ standalone│  API-роуты + серверные компоненты
                 └─────┬─────┘
                       │
                 ┌─────▼──────────────────────────┐
                 │          Postgres              │
                 │                                │
                 │  finora_control                │  реестр компаний
                 │  finora_acme     ← acme.finora.ru
                 │  finora_beta     ← beta.finora.ru
                 │  finora_demo     ← demo.finora.ru
                 └────────────────────────────────┘
```

**Ключевой принцип:** приложение одно, баз данных — по одной на компанию.
Поддомен определяет строку подключения. Код физически не может прочитать
чужие данные, даже если в запросе ошибка, — соединение открыто к другой базе.

### 2.1 Где что лежит

**`finora_control`** — только реестр:

```sql
create table companies (
  id         bigserial primary key,
  slug       text not null unique,   -- "acme" → acme.finora.ru
  name       text not null,          -- "ООО Акме"
  db_name    text not null unique,   -- "finora_acme"
  active     boolean not null default true,
  created_at timestamptz not null default now()
);
```

**`finora_<slug>`** — всё остальное: пользователи, сессии, клиенты, сделки,
касса, история. Пользователи живут внутри базы своей компании, а не в
центральной. Так «пользователь принадлежит ровно одной компании» становится
структурным фактом, а не правилом, которое нужно соблюдать в каждом запросе.

Побочный эффект: человек, работающий в двух компаниях, заводит два аккаунта.
Для вашего сценария это нормально и, пожалуй, правильно.

## 3. Схема БД компании

Ниже — целевая схема. Главное отличие от текущих типов: **всё вычислимое
перестаёт храниться**.

```sql
create extension if not exists pgcrypto;  -- для gen_random_bytes
create extension if not exists citext;    -- регистронезависимый email

create table users (
  id            bigserial primary key,
  email         citext not null unique,
  password_hash text not null,            -- argon2id
  name          text not null,            -- "Алексей Соколов"
  initials      text not null,            -- "АС" — то, что раньше было Employee.id
  role          text not null default 'manager'
                check (role in ('admin', 'manager')),
  phone         text,
  active        boolean not null default true,
  created_at    timestamptz not null default now()
);

create table sessions (
  token      text primary key,            -- 32 случайных байта в hex
  user_id    bigint not null references users(id) on delete cascade,
  expires_at timestamptz not null,
  created_at timestamptz not null default now()
);
create index on sessions (expires_at);

create table clients (
  id         text primary key,            -- "C-101", формат сохраняем ради URL
  name       text not null,
  phone      text not null default '—',
  email      text not null default '—',
  city       text not null default '—',
  since      date not null default current_date,
  created_at timestamptz not null default now()
);

create sequence deal_no start 1;

create table deals (
  id            text primary key
                default 'R-' || lpad(nextval('deal_no')::text, 4, '0'),
  client_id     text not null references clients(id),
  product       text not null,
  amount        numeric(12,2) not null check (amount > 0),
  months        int not null check (months > 0),
  markup_pct    numeric(5,2) not null,
  opened_at     date not null,
  stage         text not null
                check (stage in ('new','check','signing','active','closed','rejected')),
  manager_id    bigint references users(id),
  paid_count    int not null default 0 check (paid_count >= 0),
  next_step     text,
  deadline      date,
  reject_reason text,
  portal_token  text not null unique
                default encode(gen_random_bytes(16), 'hex'),
  created_at    timestamptz not null default now()
);

create table cash_tx (
  id          bigserial primary key,
  kind        text not null check (kind in ('purchase','payment','adjustment')),
  amount      numeric(12,2) not null,     -- минус расход, плюс приход
  occurred_at date not null,
  deal_id     text references deals(id) on delete set null,
  title       text not null,
  note        text,
  created_at  timestamptz not null default now()
);
create index on cash_tx (occurred_at);

create table deal_events (
  id          bigserial primary key,
  deal_id     text not null references deals(id) on delete cascade,
  occurred_at timestamptz not null default now(),
  text        text not null,
  user_id     bigint references users(id)
);
create index on deal_events (deal_id, occurred_at desc);

create table settings (
  key   text primary key,
  value jsonb not null
);
-- cash_opening_balance — сейчас захардкожен как CASH_OPENING_BALANCE
```

### 3.1 Что исчезло из модели и почему

| Было в коде | Судьба | Причина |
|---|---|---|
| `Deal.status`, `Deal.statusTone` | Вычисляется | Сейчас это текст из мока («Просрочка 2 дня»). У реальной сделки просрочка определяется графиком, а не полем |
| `Deal.urgent` | Вычисляется | То же самое |
| `Deal.client` (имя строкой) | JOIN к `clients` | Денормализация была нужна для быстрого рендера моков |
| `Client.status`, `statusLabel` | Вычисляется | Выводится из сделок клиента |
| `Client.nextAction`, `nextDate` | Удалить | Чистый мок, нигде не задаётся осмысленно |
| `Employee` / `seedEmployees` | Таблица `users` | Сотрудник — это пользователь с логином, а не отдельная сущность |
| `Deal.manager` (инициалы) | `manager_id` → `users.id` | Инициалы становятся производными от имени |
| `paidPayments: Record<id, число>` | `deals.paid_count` | Сохраняем как есть, см. §3.2 |

### 3.2 Осознанно оставленный долг: модель платежей

Сейчас оплата — это счётчик «сколько взносов закрыто» (`paidPayments`).
Правильно было бы хранить платежи строками: `payments(deal_id, n, amount,
paid_at)`. Это разблокировало бы честную реструктуризацию (сейчас имитация),
частичные платежи и реальные даты оплаты вместо плановых.

**Но не в эту миграцию.** Перенос на сервер и так меняет слишком много.
Если одновременно переделать модель платежей, при первом же баге будет
непонятно, что сломалось — переезд или пересчёт. Сначала переезжаем на
`paid_count`, убеждаемся что всё работает, потом отдельной задачей вводим
таблицу платежей.

## 4. Пять вещей, которые ломаются при выходе в реальный мир

Это не косметика — без этих правок сервис нельзя показывать клиентам.

### 4.1 Ссылка на кабинет клиента угадывается — уязвимость

```ts
// lib/data.ts:184 — текущая реализация
export const tokenForDeal = (dealId: string) => {
  let h = 7;
  for (const ch of dealId) h = (h * 31 + ch.charCodeAt(0)) % 46656;
  return `${dealId.slice(2).toLowerCase()}-${h.toString(36).padStart(3, "0")}`;
};
```

Токен детерминированно выводится из номера сделки, причём сам номер в него
и зашит: `R-1042` → `1042-xxx`, где `xxx` — одно из 46 656 значений. Любой
человек, получивший ссылку на свой кабинет, вычислит ссылку на чужой —
перебором в пару секунд, а то и просто поняв закономерность.

**Исправление:** колонка `portal_token` со случайным значением (уже в схеме
выше), `tokenForDeal`/`dealIdFromToken` удаляются, поиск идёт запросом по
токену. Обязательно до первого реального клиента.

### 4.2 «Сегодня» захардкожено

`TODAY_ISO = "2026-08-05"` в `lib/derive.ts` — фиксированная дата, на которую
опираются дашборд, календарь, лестница просрочки, маршрут дня. На живом
сервисе должно быть настоящее «сейчас».

Побочный эффект: затравочные данные построены вокруг этой даты и после
включения реального времени будут выглядеть протухшими. Решение простое —
**новая компания получает пустую базу**, а сиды остаются только для
демо-стенда (`demo.finora.ru`).

### 4.3 Просрочку никто не вычисляет

`addDeal`/`acceptPayment` не выставляют `statusTone`. Сейчас красный статус —
свойство мок-данных, поэтому `computeAging` вынужден на него опираться, а не
считать по датам (см. `PROGRESS_PRO.md` §5). После миграции статус считается
из графика и текущей даты — одной функцией, к которой обращаются все разделы.

### 4.4 Генерация номеров гонится

`nextId()` берёт максимум существующих и прибавляет единицу. Два менеджера,
создающих сделку одновременно, получат один номер. При 5 пользователях
вероятность мала, но это ровно тот баг, который проявится у клиента и не
воспроизведётся у вас. Лечится последовательностью Postgres — в схеме выше
уже заложено `default 'R-' || lpad(nextval('deal_no')...)`.

### 4.5 Остаток кассы — константа в коде

`CASH_OPENING_BALANCE = 1 240 000` одинаков для всех. Переезжает в таблицу
`settings`, задаётся при заведении компании.

## 5. Порядок работ

Каждый этап оставляет приложение в рабочем состоянии. Оценки — грубые, в
днях неспешной работы; при плотной работе быстрее.

### Этап 1. Postgres и схема (1–2 дня)

- Поднять Postgres локально в Docker
- Написать схему из §3 как SQL-миграции. Инструмент: `node-pg-migrate` или
  просто пронумерованные `.sql` файлы плюс табличка `schema_migrations` —
  на вашем масштабе второе честно достаточно
- Скрипт `create-tenant.ts`: создать БД, накатить миграции, завести
  админа-пользователя
- Скрипт `migrate-all.ts`: пройти циклом по `companies` и накатить новые
  миграции на каждую базу

**Готово когда:** локально создаются две тестовые базы, обе с полной схемой.

### Этап 2. Слой доступа к данным и API (3–5 дней)

- `lib/db.ts` — пул соединений на каждую компанию, **с лимитом** (см. §6.1)
- `lib/queries/` — функции `listDeals(db)`, `createDeal(db, input)` и т.д.
  Ровно те операции, которые сейчас делает `lib/store.tsx`
- API-роуты в `app/api/` — тонкие обёртки над запросами
- Перенести вычисляемое (`statusTone`, `Client.status`) в чистые функции,
  которые применяются к строкам из БД. Большая часть `lib/derive.ts` и
  `lib/data.ts` переиспользуется почти без правок — они уже принимают данные
  параметрами

**Готово когда:** `curl` к API возвращает сделки из базы.

### Этап 3. Переключение фронтенда (2–3 дня)

Здесь окупается решение вынести всё в стор: меняются **внутренности**
`lib/store.tsx`, а не страницы.

- `useState` + localStorage → загрузка через `fetch` при монтировании
- `addDeal`/`acceptPayment`/`addClient`/`addCashAdjustment` → `POST` к API
  с последующим обновлением состояния
- Состояния загрузки и ошибок — сейчас их нет вообще, потому что данные
  всегда доступны мгновенно. Появится задержка сети, её надо показывать
- Страницы, читающие через `useData()`, не трогаем

**Готово когда:** приложение работает на реальной БД, localStorage не
используется. Здесь стоит **сохранить ветку с рабочим прототипом** — на
случай если что-то пойдёт не так.

### Этап 4. Авторизация (2–3 дня)

- Страница `/login`, форма выхода
- Хеширование паролей `argon2id` (пакет `argon2`)
- Сессия: случайный токен в таблице `sessions`, кука `httpOnly`, `Secure`,
  `SameSite=Lax`, срок ~30 дней
- Middleware: нет валидной сессии → редирект на `/login`.
  Исключения — `/login` и `/pay/<token>` (кабинет клиента без входа)
- Управление сотрудниками на `/employees`: пригласить, деактивировать,
  сменить роль. Раздел уже есть, добавляются действия
- Имя пользователя на Главной вместо захардкоженного «Алексей»

**Готово когда:** без входа ничего не открывается, вход работает.

### Этап 5. Многотенантность (1–2 дня)

- Middleware: `Host` → `slug` → компания из `finora_control` → БД в контекст
  запроса
- Неизвестный поддомен → понятная страница «компания не найдена»
- Корневой `finora.ru` → лендинг или редирект на форму входа
- Скрипт заведения компании: создать запись в реестре, создать БД, накатить
  схему, создать администратора

**Готово когда:** локально работают два поддомена с разными данными.
Проверить через `/etc/hosts`: `acme.finora.local`, `beta.finora.local`.

### Этап 6. Правки из §4 (1–2 дня)

Случайные токены кабинета, реальное «сегодня», вычисляемая просрочка,
номера через последовательность, остаток кассы в настройках.

### Этап 7. Docker и деплой (2–3 дня)

См. §7.

### Этап 8. Бэкапы и запуск (1–2 дня)

См. §8. **Первого клиента заводим только после того, как проверено
восстановление из резервной копии.**

**Итого:** ориентировочно 13–22 дня работы. Основное — этапы 2–4, и они
одинаковы независимо от выбранной топологии.

## 6. Технические ловушки

### 6.1 Соединения с БД при отдельной базе на компанию

Наивный подход — пул на каждую компанию с настройками по умолчанию
(`max: 10`) — даёт 100 соединений при 10 компаниях, а `max_connections` в
Postgres по умолчанию как раз 100. Плюс hot-reload в разработке плодит пулы.

```ts
// lib/db.ts
const pools = new Map<string, Pool>();

export function getPool(dbName: string) {
  let pool = pools.get(dbName);
  if (!pool) {
    pool = new Pool({
      connectionString: `${process.env.PG_BASE_URL}/${dbName}`,
      max: 3,                      // не по умолчанию! 10 компаний × 3 = 30
      idleTimeoutMillis: 30_000,   // отпускать простаивающие
    });
    pools.set(dbName, pool);
  }
  return pool;
}
```

Пулы создаются лениво — компания, в которую сегодня никто не заходил, не
держит соединений. При 10 компаниях этого достаточно с большим запасом.

### 6.2 Сборка Next.js на сервере съест память

`next build` на 4 ГБ RAM рядом с работающим Postgres может уйти в OOM.
Варианты:

- Собирать образ локально и пушить в реестр (Docker Hub приватный, или
  реестр вашего провайдера) — предпочтительно
- Либо временно добавить swap на сервере

### 6.3 `output: 'standalone'`

В `next.config.ts` сейчас пусто. Для Docker нужно:

```ts
const nextConfig: NextConfig = {
  output: "standalone",
};
```

Иначе в образ поедут все `node_modules` — сотни мегабайт вместо десятков.

### 6.4 Ловушка префиксов путей остаётся актуальной

`components/shell.tsx` проверяет `pathname.startsWith("/pay/")` — со слэшем,
иначе под условие попадёт `/payments` (уже ловили этот баг). При добавлении
`/login` и `/api` проверить, что новые пути не являются префиксами
существующих.

## 7. Docker и веб-сервер

### 7.1 Состав

```yaml
# docker-compose.yml — скелет
services:
  caddy:
    image: caddy:2-alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro
      - caddy_data:/data          # сертификаты, обязательно том!
      - caddy_config:/config
    restart: unless-stopped

  app:
    image: finora:latest          # собран локально, запушен в реестр
    environment:
      PG_BASE_URL: postgres://finora:${PG_PASSWORD}@db:5432
      CONTROL_DB: finora_control
      SESSION_SECRET: ${SESSION_SECRET}
    depends_on: [db]
    restart: unless-stopped

  db:
    image: postgres:17-alpine
    environment:
      POSTGRES_USER: finora
      POSTGRES_PASSWORD: ${PG_PASSWORD}
    volumes:
      - pg_data:/var/lib/postgresql/data
    restart: unless-stopped
    # порт наружу НЕ пробрасываем — только внутренняя сеть

volumes:
  caddy_data:
  caddy_config:
  pg_data:
```

Секреты — в `.env` рядом с compose-файлом, права `600`, в git не коммитить.

### 7.2 Caddy: сертификаты без API-токена DNS

Обычный путь для `*.finora.ru` — wildcard-сертификат через DNS-01, а для
этого нужен плагин под вашего DNS-провайдера и API-токен. У российских
регистраторов с этим бывает по-разному.

**Проще:** выдавать сертификаты по требованию, на каждый поддомен отдельно.
Работает по HTTP-01, никаких токенов:

```
{
  on_demand_tls {
    ask http://app:3000/api/internal/tls-check
  }
}

https:// {
  tls {
    on_demand
  }
  reverse_proxy app:3000
}
```

Эндпоинт `/api/internal/tls-check?domain=acme.finora.ru` обязателен: он
проверяет, что такая компания есть в реестре, и отвечает `200` или `404`.
Без него любой, направив свой домен на ваш IP, заставит сервер выпускать
сертификаты и упрётся в лимиты Let's Encrypt.

При 10 компаниях это идеальный вариант. Wildcard имеет смысл, когда
поддоменов сотни.

### 7.3 Процесс выката

```
локально:  docker build → docker push
на сервере: docker compose pull && docker compose up -d
            docker compose exec app node scripts/migrate-all.js
```

Миграции гоняются отдельной командой после запуска, а не в `CMD` контейнера:
иначе при рестарте они будут пытаться выполниться повторно и параллельно.

Откат: `docker compose` на предыдущий тег образа. Поэтому **теги должны быть
версионными** (`finora:2026-08-15`), а не только `latest`.

## 8. Резервные копии

Единственный раздел, который нельзя отложить «на потом»: данных у клиентов
нет нигде, кроме вашего сервера.

- Ежедневный `pg_dump` каждой базы + `pg_dumpall --globals-only` для ролей
- Складывать **в объектное хранилище** (S3-совместимое), не на тот же диск.
  Копия рядом с базой не переживёт смерть сервера
- Хранение: 7 ежедневных + 4 еженедельных
- Шифровать перед отправкой — там паспортные данные

```bash
# скелет скрипта, по cron раз в сутки
for db in $(psql -tAc "select db_name from companies where active"); do
  pg_dump -Fc "$db" | age -r "$AGE_KEY" > "/tmp/$db-$(date +%F).dump.age"
  # → отправка в хранилище
done
```

**Проверка восстановления — обязательный шаг, а не пожелание.** Раз в
квартал: поднять дамп в отдельную базу, зайти, убедиться что данные на месте.
Непроверенная резервная копия равносильна её отсутствию.

### Мониторинг по минимуму

- Внешняя проверка доступности (UptimeRobot и подобные) на `/api/health`
- Оповещение о заполнении диска на 80% — самая частая причина падения
  Postgres на маленьких серверах
- `docker compose logs` и `restart: unless-stopped` для автоперезапуска

Полноценный Prometheus/Grafana на этом масштабе не нужен.

## 9. Заведение новой компании

Целевой процесс (одна команда):

```
docker compose exec app node scripts/create-tenant.js \
  --slug acme --name "ООО Акме" --admin-email a@acme.ru
```

Что происходит: запись в `finora_control` → `CREATE DATABASE finora_acme` →
миграции → администратор с временным паролем → базовые настройки (остаток
кассы). Клиент заходит на `acme.finora.ru` и **видит пустую CRM** — сотрудники,
клиенты и сделки заводятся им самим. Сиды остаются только на демо-стенде.

Удаление компании: `pg_dump` на прощание (отдать клиенту его данные),
`active = false`, через оговорённый срок — `DROP DATABASE`.

## 10. Порядок действий прямо сейчас

1. Выяснить вопрос с 152-ФЗ и паспортными данными — это может изменить выбор
   хостинга, а значит и всё остальное

по ходу — он не блокирует старт.
